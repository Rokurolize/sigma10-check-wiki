# KB-25 — WebKit-only absence of the mobile sidebar-open control (betwixt class)

- **Class:** B. Theme defect, triage only
- **Detection cost:** needs live probe
- **Provability:** TRIAGE
- **Evidence source:** R/KNOWLEDGE-SEED-INVENTORY.md (compiled 2026-11-17 from the GOSIGN2 review reports and coordinator adjudications named there).

## Mechanism

The theme re-implements the mobile sidebar toggle (`.open-menu a`, the
hamburger). Some combination of its own rules and the base's WebKit-specific
cascade (a `-webkit-` prefixed rule, a display/visibility interaction, or a
transform the Chromium build tolerates) removes the control entirely in WebKit
at 375/320 while Chromium renders it. The sidebar exists but no reader on a
WebKit phone can open it.

## Static detection

Triage signal only: the candidate carries its OWN `.open-menu` / `#side-bar`
rules (count them; themes that purely inherit the base are lower risk, not
zero), especially with `-webkit-` mentions or engine-specific prefixes near the
toggle rules. Rank themes with own sidebar re-implementation first for the
WebKit mobile screenshot comparison.

## Confirmed instances

betwixt, page and sample: hamburger present in Chromium, entirely absent in
WebKit at 375x812 and 320x640, machine `sidebar-unreachable` on all four mobile
combos, confirmed by direct screenshot comparison: RENDER-S2-RERUN16 +
RENDER-ROWS-RERUN16-PARTIAL. Static prediction in the same partial file flagged
exactly this risk class for magicity and marchen before their runs (marchen
confirmed in the sibling form KB-26).

## False positives and disposition

A missing `*-sidebar.png` capture alone is not the finding (screenshot ceiling,
KB-46); the finding is the control's absence in the full-page WebKit capture vs
its presence in Chromium at the same viewport.

## Fix

Correct the theme's toggle rules so the control renders in WebKit (the specific
declaration is per-theme; the pattern is the engine split).
