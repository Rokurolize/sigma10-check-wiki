# KB-75 — Split delivery whose parts live outside the canonical repo

- **Class:** F. Named exception / standing disposition
- **Detection cost:** pure grep
- **Provability:** FILE-PROVABLE
- **Status:** adopted
- **Basis:** lane-report
- **Dedupe key:** split delivery / an original serving N code files while the candidate file carries part 1 only and a banner declares where parts 2..N live / banner-plus-repo census
- **Support:** 1 (lane-report)
- **Evidence source:** R/review-scout/BATCH-MPURE8.md proposal P3 (ordopharm three-part shape).

## Mechanism

Some originals deliver their CSS as N separate code files. The port's
candidate carries part 1 only, with a banner declaring where parts 2..N
live. When that declaration cites a lane record that is not in the
canonical repo, a PASS read as completeness is unfounded: the reviewer
cannot verify the other parts exist. This is a completeness disposition,
not a rendering defect.

## Static detection

For each candidate whose delivery banner declares multiple parts, census
the repo for the named part pages and record which are present. A banner
whose cited location resolves outside the canonical repo is the hit.

## Confirmed instances

ordopharm (three-part original; candidate carries part 1, split declared
in a banner citing INTEGRATION.md, which is not in the canonical repo).

## False positives and disposition

A single-code-file original is not this pattern. A split whose parts are
all present as canonical include-target pages is a recorded, complete
split, not a hit.

## Fix

Add a sources.tsv flag / named class for split deliveries so a review can
verify every part exists before PASS is read as completeness. Bring the
cited record into the canonical repo, or name the canonical fullnames of
all parts in the banner.
