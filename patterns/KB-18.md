# KB-18 — Untranslated visible text, including CSS `content:` strings (pattern 10 / T5)

- **Class:** A. Theme defect, file-provable
- **Detection cost:** cross-file diff
- **Provability:** FILE-PROVABLE
- **Status:** adopted
- **Basis:** static-diff, lane-report
- **Dedupe key:** visible text / untranslated reader-visible string in body, usage text, or a CSS content: string / content: scan plus prose scan, T5 judgment
- **Support:** 2 (static-diff, lane-report)
- **Evidence source:** R/KNOWLEDGE-SEED-INVENTORY.md (compiled 2026-11-17 from the GOSIGN2 review reports and coordinator adjudications named there).

## Mechanism

Reader-visible strings survive translation in three hiding places: body/usage
text left in the original language, sample/exhibit text, and CSS `content:`
strings (labels, badges, pseudo-element text) that no wikitext scan sees. After
migration these render as foreign-language UI on the JP wiki.

## Static detection

Grep the candidate for `content:` declarations and read every string value; scan
body and usage sections for untranslated prose (headings, button labels, sample
text). Judge against the original: in-universe proper nouns are intentional
residue (see false positives).

## Confirmed instances

ad-abyssum-penumbra: untranslated Hebrew CSS strings (RENDER-S2-A summary,
section 5/T5). cosmonaut: untranslated "by Some Dude" in the reader-visible fake
footer sample (LOCALIZE-A row 7). aesthetic: stale reader-visible font name in
usage text (T5 finding 1).

## False positives and disposition

EN in-universe proper nouns (UIU/FBI, SPC DATABASE, GoI names) are intentional,
not findings. Plain 翻訳責任者 wording and 元記事リンク link text other than the 原題 are a
once-per-report uniform nit, not per-row failures (AGENTS.md section 3 T5).

## Fix

Translate the string in the candidate (CSS `content:` included), keeping
in-universe nouns.

## Amendment (2026-11-17, documentation-pass taxonomy review): string-valued variables, and glyph-form conversion

The Mechanism above names body text, sample text, and CSS `content:`
strings. Two more hiding places sit outside that naming, both
reader-visible when rendered:

String-valued custom properties. Themes carry UI text in CSS
variables that are not `content:` declarations: rate-widget labels,
lock notices, theme names (the --RATE_text / --RATE_text_HOV,
--lock-info111/222/333 and _MOB, --theme-name, --ink-title-a shapes).
A wikitext prose scan never sees them and a `content:`-only grep
never sees them; they render as UI text all the same. Detection
extends accordingly: grep both CSS channels for custom properties
whose value is a quoted string containing natural-language text
(excluding font names, URLs, and pure keyword values), and judge each
string as for `content:`. Confirmed as a hiding place by the
documentation-pass taxonomy sample (2026-11-17): magazine (--RATE_text
pair at candidate L249-250; the --lock-info111/222/333 lock-notice set
at L542-544, Japanese in the candidate), uiu-bhl-theme (--theme-name
at L211), sodium and ink (string-valued variables across the file),
steam-guide (@@-exhibited --title/--subtitle examples, judged as
exhibit text). The point of the instance list is the scan: in an
unported file these same variables carry the original's language
invisibly to the old recipe.

Glyph-form conversion (named sub-shape). A retained string can be
neither translated nor untouched: CN-original strings kept as text
but converted from simplified/traditional glyph forms to Japanese
shinjitai, with punctuation forms converted alongside (ink:
中華異學會 -> 中華異学会; 格异·治学·融会 -> 格異・治学・融会). This is a
deliberate, correct outcome, not untranslated residue; the
explanation records it as glyph-form conversion so a reviewer diffing
strings reads it as neither a translation nor a miss. Detection:
candidate strings differing from the original's only in glyph or
punctuation forms of the same characters. A string left in simplified
forms where the theme's other retained strings were converted is the
chargeable inconsistency, not the conversion itself.
